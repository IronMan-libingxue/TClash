# A 端设备扩容与重新分发：设计与验收方案

状态：**用户已对齐设备、改名与从零开始的清理边界，授权按本方案改造。设计和验收目标不代表改造或 Windows 实机验收已经完成。**

整理日期：2026-11-14（北京时间）。本文补充原有 [TClash Preview 设计与验收方案](01-Preview立项与验收.md) 和 [四项改造及 Fast／多会话验收方案](02-原四项改造与监控.md)。具体变更以本文及后续确认的清理范围为准；原文中五台远端设备的范围在本轮扩为下列八个预设位置。

## 一、已对齐的需求

1. **A 端仍独立**：本机默认名称为 Mac 1，保留本机已有用量、账号官方额度、私库连接和 A 端凭证。TClash 只集成 B 端。
2. **设备位置**：在本机以外预留 Mac 2、Mac 3、Mac 4、Mac 5、Mac 6、Windows 1、Windows 2、Windows 3，共八个远端预设位置。可以分批添加，无需立即安装或配置所有设备。
3. **可自定义名称**：Mac 1 及各 B 设备均可在 A 端自行更改显示名称。预设编号是默认名称；名称变更不得改变设备身份、重建配对、混淆设备、改动历史记录或改变同步倍率。
4. **其他设备重新测试**：用户明确希望清理原来保留的其他设备令牌，重新分发连接；Windows 1 不接续旧的 B 端历史，按全新设备测试。Mac 1 的数据和 A 端凭证保留。
5. **令牌输入**：每台 B 使用独立的、仅限所需私库的访问令牌；令牌由用户在本机应用或 GitHub 的相应界面输入，不通过聊天发送。A 端凭证不放入 B 安装包。
6. **保留统计口径**：A 显示原始用量；B 端默认显示设备实际全量的 1.5 倍，系数和参考预算仍由 A 端管理。官方额度属于账号，不是设备额度。

## 二、已确认的清理边界

- 用户确认：清除 A 保存的旧远端设备配对和旧统计，并移除私库当前文件中的旧设备统计；新 B 从首次接入时开始计数。保留 Mac 1 的数据和各设备的 Codex 原始日志。
- GitHub 既往提交中的旧文件可能仍然存在；本次不重写提交历史，不删除整个私库。私库中其他无关内容与 A 端凭证保持不变。
- 旧 B 的 GitHub 访问令牌要在提供方实际撤销并核对。只清除本地文件或取消 A 端设备登记，不能证明旧 GitHub 令牌已失效；未连接设备上的本地令牌需要在对应设备上处理。
- 先准备并验证新版、清理清单及重新授权流程，再执行真实清理；清除操作必须限制于已识别的旧 B，避免影响 Mac 1 和无关 GitHub 令牌。

## 三、改造前基线

- A 端当前已登记一台真实远端设备：Windows 1。当前旧安装材料中含设备专用授权；A 端自身私库凭证、旧设备令牌和用量不得输出到日志或聊天。
- 现有预设位置是 Mac 2～Mac 4 与 Windows 1～Windows 2；位置列表、安装包生成、界面、模拟设备及部分测试按五台远端设备编写，不能只改界面文字。
- 现有 Windows 迁移方式意在接续旧身份和令牌，不符合本轮从零测试目标；其安装脚本在目标程序已存在时也可能跳过安装。不能将旧迁移包当作本轮新版从零安装的验收依据。
- 现有用量读取会扫描已有 Codex 日志；如果要求新设备从某一时刻开始计数，需要增加可持久化的统计起点，而不能通过删除原始 Codex 日志实现。
- 当前 A 的同步间隔曾由用户设为 1 分钟；扩容时保留已有设置。新配置的设计默认仍为 5 分钟，可在 A 端调整。
- 当前 A 和 TClash 的业务代码、安装材料和相关工作区存在未提交改造，实施前应保存可回退的程序和必要配置基线，不覆盖其他工作。原 Codex 配置和 TClash 代理配置不因本轮设备管理而改变。

## 四、技术路线

- **技术栈**：沿用现有独立 A 的 Go/Wails 用量采集和界面，以及 TClash 的 Tauri/Rust、React/TypeScript 和内置 Go 采集器；沿用 GitHub 私有仓库、设备签名与用量加密机制。
- **设备编号与名称分离**：设备预设位置和设备身份使用稳定标识，显示名称单独保存。A 的总览、设备选择、明细、同步设置和安装材料管理应对同一设备显示一致名称；同名设备必须仍能区分，输入不能改变文件路径或破坏界面。
- **容量与旧版本兼容**：A 中统一维护八个预设位置，前后端安装包选项和设备卡片使用同一来源。旧有五台演示数据仍应可读取，新增位置可以显示未接入；模拟数据继续明确标记并排除在真实汇总之外。
- **从零开始机制**：新 B 首次运行并应用安装授权时记录统计起点；即使当时离线，也从这个本机激活时间开始，后续联网再同步。按该边界筛选 Token 和历史额度读取记录，避免旧日志重新回流；重启、离线和重新同步不得重置该起点。官方周期信息仍用于划分当前周期，不代表设备从周期开始就已被采集。
- **重发与安装**：为各预设位置按需生成新的设备专用安装材料。Windows 1 采用新的设备授权；安装过程必须确认新版确实安装或更新，在已有 TClash 的情况下也不跳过，并防止旧 B 与新 B 重复采集。其他设备尚未就绪时保持未接入状态。
- **旧记录与令牌**：本机旧安装材料、旧设备身份、私库当前文件、GitHub 令牌及 Git 历史分别盘点和处理；Git 历史按用户确认保留。清理结果分别记录为“已清理”“待用户在对应设备处理”或“无法验证”，不以本机文件删除冒充提供方撤销。
- **配置保护**：不更改 Codex 原始日志、Codex 设置、TClash 订阅及代理规则；安装与接入异常时给出明确状态。历史清除与令牌撤销一旦执行，不能承诺旧连接仍可直接恢复。

## 五、验收条件

1. A 本机加八个预设远端位置均可在界面识别；Mac 5、Mac 6、Windows 3 可实际生成各自的 TClash 安装材料。
2. 对 Mac 1 和已接入 B 分别更名，重启 A 后名称仍正确；设备身份、历史归属、同步设置和 B 倍率不变；同名或非法名称的处理明确，不产生混淆或路径问题。
3. 原五台远端演示场景可继续运行，真实设备和模拟设备不混入对方汇总；新增空位置不伪造用量。
4. 用不含真实令牌的模拟样本验证八台设备的分别授权、自动接入、隔离、同步、断线恢复、重复安装和重复上传去重；新设备无法继承其他位置的凭证。
5. 按已确认的清理方案验证其他设备从零开始，旧用量不会重新进入 A；保留 Mac 1 原有统计、官方额度读取和 A 私库凭证。
6. B 使用真实原始记录，A 显示原值，B 按设备当前系数显示；缓存开关、项目/模型明细、参考美元和占比保持原有口径。
7. Windows 1 实机：确认操作系统架构和已有程序状态；安装正确的新版 TClash，完成新授权；A 只出现一个对应设备，旧独立 B 不重复上传。分别核对新产生的用量、设备改名、重启、断网恢复和私库同步时间。未实测成功前不得宣称已验收。
8. 安装包不含 A 的解密密钥或 A 端令牌；旧令牌处理、私库文件和历史提交状态按实际结果报告，不把本地清理误称为 GitHub 已撤销。

## 六、实施与验证顺序

1. 按已确认的旧数据和令牌清理范围，形成可审阅的设备与数据清单。
2. 更新 A 的设备位置与名称管理，在隔离环境验证扩容、改名、旧模拟数据及现有统计不回归。
3. 按确定的从零边界实现新设备初始统计、旧授权处理及 TClash 安装材料，在不使用真实令牌的环境完成验证。
4. 构建本机预览及 Windows 安装材料，保护现有 A 和 TClash；真实授权和私库变更按确认范围执行。
5. 与用户配合在 Windows 1 实机安装和验证，再按需为其他设备分发；记录未完成的实机项目，不用模拟结果代替。

## 七、后续正式版的一键交付要求

- 每台 B 设备交付一个包含对应设备授权和完整 TClash 的安装包：Windows 使用单个可执行安装包，Mac 使用可双击的安装应用。安装、更新、授权加载和首次自动接入由安装包处理，不要求再运行补丁、脚本或其他工具。
- 安装时识别已有程序和设备身份，保留原有代理配置与 Codex 日志；不兼容的既有连接或多个有效安装位置必须明确提示，避免错误覆盖或重复统计。安装失败时不能提前停用原有采集程序的自动启动。
- 用户可按系统或安装程序的正常提示退出旧程序、确认安装。自动接入仍依赖设备能够访问私库，以及 A 端在线同步；设备授权仅随该设备安装包私下分发。
- Windows 1 的一键安装和 A 端接收由用户于 2026-11-14 实机确认。Mac 的一键安装除本机隔离测试外，还须在真实远端 Mac 上确认启动、授权加载和 A 端接收；Intel、Apple 芯片及 Windows 各架构的验收以实际设备结果分别记录。
- 交付正式版前应核对签名与平台提示，确保用户拿到单个完整安装材料；不能把自签名预览、构建成功或模拟测试等同于正式发布及实机验收。
