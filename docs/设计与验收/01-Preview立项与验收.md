# TClash Preview 设计与验收方案

**后续设备扩容（2026-11-14）**：原方案中五台远端设备的范围已扩展，改名及旧设备从零重发的具体边界见 [设备扩容与重新分发方案](03-A端扩容与重新分发.md)。本条为后续补充，不代表 Windows 实机验收已经通过。

状态：供确认的设计方案。确认前不实施改造。

## 一、需求理解

TClash Preview（简称 TClash）以 Clash Verge Rev 为基础，在完整代理界面中集成现有的 Codex 用量 B 端。**A 端和 TClash 是两个独立、完整的应用：A 端继续使用现有的「Codex 用量.app」作为唯一主控端；集成进 TClash 的只有 B 端。**

- **A 端「Codex 用量.app」**：继续独立安装和运行，读取本机真实用量与可读取的官方账号额度，并集中查看各 B 设备的实际用量、设备和模型等明细。设备授权、同步频率和展示系数仍由 A 端管理。A 端不依赖同一台设备安装或启动 TClash 才能使用这些功能。
- **TClash 的 B 端**：作为 TClash 内的 CodeX Speed 页面和自动运行的采集功能，读取所在设备的本机日志，显示 B 端简化用量，并向共同的私有存储加密同步实际统计。TClash 不包含或替代 A 端主控界面。
- **两端关系**：A 与各台 B 通过共同可访问的私有存储交换已授权的统计数据和设置，双方无需在同一网络，也无需同时在线。A 未运行时，B 按同步条件继续上传；A 下次联网运行后读取已上传的数据。
- **原有 A 端保护**：保留已验收的 A 端界面、本机真实统计、设备数据和功能。为生成设备专用 TClash 安装材料及兼容新 B 而可能进行的必要调整，仍发生在独立 A 端内，并需通过原功能回归验收。

- 侧栏在截图中「设置」的下方增加 **CodeX Speed**，图标使用 Codex 标识。点击后在 TClash 窗口内进入 B 端用量页面。
- TClash 启动后自动启动 B 端采集。页面保留现有 B 端的项目、模型、周期、含缓存开关、本机模型速度与同步状态，不增加 B 端手动同步或设置页面。
- 默认显示 Token 和参考美元分别按真实值乘 1.5，具体系数由 A 端控制。A 端接收加密后的实际统计数据；速度只在产生它的本机显示。
- 兼容 Clash Verge Rev 支持的订阅、YAML、备份和代理协议。TClash 导出的专用文件供 TClash 使用；代理内核在运行时继续使用标准配置。
- 首轮在 macOS 和 Windows 验收。上游 Linux 支持保留为后续适配范围。
- 首版通过手动安装更新；安装后默认将 `clash://`、`clash-verge://` 订阅链接交给 TClash 处理。
- 关于 Codex 网络路径，用户已确认保持 Clash Verge Rev 原有代理规则。系统代理或 TUN 生效时，Codex 可能按照所选规则走代理；这一选择调整了此前「Codex 不走代理」的要求。用量采集仍独立读取本机日志，不需要代理 Codex 请求。

## 三、技术栈与集成路线

### 1. 应用主体

- 沿用 Clash Verge Rev 的 Tauri 2、Rust、React、TypeScript、Vite、MUI 和 pnpm；代理引擎沿用上游对应版本的 Mihomo。现有 Codex 采集、计价和同步逻辑沿用 Go。
- 在 React 侧栏、路由和多语言资源中增加 CodeX Speed；页面适配原版浅色、深色、窗口缩放和侧栏布局。Codex 图标优先核对并使用现有项目中的 Codex 图形资源，实际显示效果在界面验收时确认。侧栏品牌、窗口标题、托盘、安装包和关于页面使用 TClash Preview 名称。
- 将现有 Go B 的采集和同步部分拆成可随 TClash 打包的后台组件，由 TClash 的 Rust 主进程管理生命周期。它不再启动 Wails 窗口或独立托盘图标；侧栏页面通过受限制的本机通信读取 B 端原本允许展示的汇总结果。
- 打开 TClash 后自动启动采集，窗口隐藏到托盘时继续运行；真正退出 TClash 后停止本次随应用启动的采集进程，下次启动后从已有日志补读。发生采集或同步错误时在 CodeX Speed 页面显示状态，代理主程序继续工作。
- B 的本地读取和向私库同步使用现有的独立用量链路。该集成不改 Codex 配置、不将采集功能接入代理内核或 Codex 请求链，也不额外添加 Codex 强制直连规则。系统代理和 TUN 保持上游的工作方式；如果它们覆盖 Codex 流量，Codex 的网络路径仍受所选规则影响。

### 2. 设备接入与现有 B 处理

- 沿用已验收的 A/B 设备身份、私库、签名、加密数据与设置格式，继续使用 A 端下发的默认 5 分钟间隔及可调整系数。
- 新设备使用 A 端一次预授权，形成该设备专用的 TClash 安装材料。安装后自动启动 B 并完成登记；通用未授权安装包可以展示本机用量，并提示尚未连接 A。具体打包入口需在现有 A 端增加 TClash 安装材料生成能力，A 端用量统计和已接入设备保持兼容。
- 现有 Windows 1 的独立 B 是功能测试。建议同机安装 TClash 时优先安全接续原设备身份与授权，在新采集端验证成功后交接旧采集进程及其自启动，确保 A 只显示一台 Windows 1。交接前保留可恢复备份；失败时保留原有连接。最终交接细节作为本方案的一部分供确认。
- 避免同一设备同时运行两份采集并重复计数。本机同时运行 Mac A 和测试 B 时，使用隔离测试接收端或明确排除重复记录；不将同一份本机日志当成两台真实设备计入 A 的正式总计。
- 保留设备专用令牌和授权材料的私有属性。TClash 的代理配置导出、日志和错误提示不包含 A 的解密钥匙或 B 的私库令牌。
- 现有 A 的多账号查看已实现，但现有 B 的历史请求跨账号归属尚未完整验证。集成不把参考美元、设备占比或当前账号推定当作官方逐设备扣费；账号切换时的归属与不确定状态需单独实测。

### 3. 同步与网络状态

- 正常在线时，B 默认约每 5 分钟上传变化，A 按现有频率读取。实际可见时间还取决于日志落盘、A 的读取周期、网络和设备休眠。
- 后台组件断网时仍应定时更新本机页面；联网后从本机日志补读并恢复增量同步。当前 B 的同步流程在持续连接失败时不会每轮刷新本机统计，集成时需要补齐这一行为并验证。
- 以现有 B 的周期、缓存、输入/输出 Token、模型价格、项目和模型统计为基准逐项对账。参考金额和 $900 周期基数是估算；官方账号额度与单设备或单模型估算分开解释。

## 四、配置文件单向兼容方案

| 内容 | TClash | Clash Verge Rev |
| --- | --- | --- |
| Clash Verge Rev 支持的 YAML、订阅链接和原版备份 ZIP | 直接导入，按上游语义处理 | 按原版功能使用 |
| TClash 导出的单配置或完整备份 `.tclash` | 识别、校验、导入和恢复 | 原版不能直接作为有效配置或备份恢复 |
| 标准代理订阅链接、协议和运行时配置 | 继续支持 | 继续按原版支持情况使用 |

建议的 `.tclash` 使用专用文件标识、格式版本、内容类别、打包内容与完整性校验。打包内容采用带专用标识的编码容器，而非仅更换文件名或注释；对 YAML、配置关联、节点、规则、脚本及备份中上游支持的内容保持可还原。TClash 导入前先校验并在隔离目录准备，成功后再应用；失败保留原有配置。

本地导出、自动备份以及代理配置的 WebDAV 备份均需纳入专用格式适配；恢复时继续接受上游原版 ZIP。代理配置备份与 Codex 用量使用的 GitHub 私库是各自独立的功能，测试分别核对。

该设计满足「专用文件不能直接导入原版」的边界，属于格式兼容控制。因为标准代理配置最终仍需交给 Mihomo，有意提取或转换内容的人可以得到标准格式。订阅链接和代理协议本身继续遵循原有协议。

上游 2.5.10 的本地备份导入先检查 `.zip` 后缀并复制文件，真正恢复时才解析 ZIP。因此验收既检查 `.tclash` 原名不能作为原版备份恢复，也检查改名为 `.zip` 后依然不能成功恢复；原版可能先把改名文件列入备份列表。YAML 入口以无法激活为有效代理配置为准。[上游备份实现](https://github.com/clash-verge-rev/clash-verge-rev/blob/v2.5.10/src-tauri/src/feat/backup.rs)

## 五、独立安装、更新与开源

- 应用名称、标识、数据目录、单实例锁、日志、托盘与自启动标识使用 TClash 独立命名。上游服务模式使用固定服务标识和独立服务组件，需要专门核查并处理服务、IPC 与安装卸载的冲突；不能只改应用图标和名称。服务模式在两个应用并存时的具体隔离方式需实现并实测后才能确认。
- 安装时将 Clash 订阅链接默认交给 TClash。方案应记录原默认处理方式，提供恢复方法，并验证卸载或改回默认后原版仍可使用。系统对默认应用切换若要求用户确认，按系统界面完成。
- 两个应用可分别安装，但同时占用相同代理端口、系统代理或 TUN 时需要冲突提示和明确的控制归属。验收中不得静默覆盖正在使用的配置。
- 首版手动安装更新，移除原版应用自动更新入口的直接覆盖路径，界面明确显示手动更新。后续如恢复自动更新，使用 TClash 独立的发布地址和签名。
- Clash Verge Rev 采用 GPL-3.0-only，现有 Magpie 基础代码采用 MIT。分发时保留对应许可、版权和修改说明，并按适用许可提供源码及第三方声明。[Clash Verge Rev 许可](https://github.com/clash-verge-rev/clash-verge-rev/blob/v2.5.10/LICENSE)、[现有 Magpie 许可](../codex-usage-tracker/LICENSE)

| 阶段 | 验收条件 |
| --- | --- |
| 原版基线 | 在隔离环境记录 2.5.10 的功能、测试结果、内核版本和配置样本；保留当前 TClash 开始前的源代码与现有 B 代码快照。 |

| UI | 侧栏「设置」下方出现 Codex 图标与 CodeX Speed。点击后在同一窗口进入 B 用量页；浅色、深色、窗口缩放均可用，原有导航和设置继续工作。 |

| 双端运行与同机去重 | B 与 A 分别离线或不同时在线后重新联网时，A 可读取已成功上传的数据；A 端和 TClash 同机运行时，同一份本机用量不会被计入两台真实设备或重复计入总量。 |
| 生命周期 | 隐藏到托盘后采集继续，退出 TClash 后按设计停止；重新启动可补读。断网后本机统计继续更新，恢复联网后补传；重复上传、重启和快速开关不会重复累计。 |
| 原版兼容 | 上游代表性 YAML、订阅、ZIP 备份、Merge、Script、规则、代理组、DNS、供应商及已有资源路径，在同版本内核下与原版产生一致的配置语义和代理行为。使用上游测试和样本矩阵覆盖；发现未覆盖差异时明确记录并修复。 |
| Codex 网络路径 | 不修改 Codex 配置，不为采集额外改变代理规则。在可用的 macOS 和 Windows 测试环境中，分别核对系统代理和 TUN 等模式下 Codex 的实际网络路径符合所选配置，并清楚标注可能经代理；不将「始终直连」作为验收条件。 |
| 单向文件兼容 | TClash 接受原版样本与 `.tclash`；本地及 WebDAV 备份可往返恢复。完整性错误、版本不支持或文件损坏时给出提示并保留旧配置。原版不能直接使用 `.tclash`，改名后的文件无法成功作为有效配置激活或作为 ZIP 备份恢复。 |
| 共存与更新 | 安装后 `clash://` 与 `clash-verge://` 按所选默认交给 TClash；可恢复原默认。原版应用及配置可继续打开。服务、端口或系统代理冲突有明确提示，不偷偷改变另一应用。手动更新保留 TClash 的配置、设备身份和统计。 |
| 平台实机 | 首轮分别验证 macOS Apple Silicon/Intel 与 Windows x64/ARM64 的构建；在实际可用的 Mac 和 Windows 设备上验证安装、启动、托盘、代理模式、同步和配置导入。构建成功不等于对应架构实机通过。 |

## 七、验收边界和后续条件

- 本轮优先按用户提供的 Mac 和 Windows 环境验收。Linux 的上游代码支持保留，Linux B 集成与实际验收以后安排。
- 尽量用不包含真实节点和令牌的样本做自动测试；涉及实际订阅、真实系统代理、TUN 或 Windows 设备的最终验收，需要相应真实环境和可恢复的测试安排。
- 首版是手动更新的 Preview；正式发布位置、发布签名、更新服务及公开分发方式待后续决定。
- 「兼容所有上游功能和配置」是设计目标，验收使用固定上游版本、上游测试及覆盖协议和配置类型的差异测试。未覆盖的特殊配置以及上游未来新增能力需单独验证，不能在实施前宣称已经全部兼容。

## 八、本机预览进度（2026-11-13）

以下仅记录本次已经核对的结果，不改变上面的完整验收标准：

- Mac 预览窗口能够显示本机真实 Codex 用量和本机模型速度估算；已实测识别当前用户同机 A 端后暂停 B 上传，避免作为第二台设备重复统计。该识别当前以同一操作系统用户的数据目录为范围。
- 使用无真实节点的样本，在 TClash 图形界面完成标准 YAML 导入、`.tclash` 单配置导出和回读；标准 Mihomo 接受该 YAML 并拒绝该专用文件。还在界面中创建专用备份，并用预览配置生成标准 ZIP 实际导入、恢复。备份回滚、模拟 A/B 加密同步、倍率、离线刷新及同步周期通过本地自动检查。
